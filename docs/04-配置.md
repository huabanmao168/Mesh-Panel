# 第 4 块：SS 配置生成 + 推送 + reload

## 目标

每个节点能在 Web 界面填一份 SS 配置（端口/密码/加密 + DNS），点保存
→ 主控生成 sing-box JSON
→ SSH 推送到节点 `/etc/sing-box/config.json`
→ WS 触发 agent 执行 reload
→ 节点上 sing-box 平滑切换配置（不断线）

## 数据模型

`nodes` 表加一列 `ss_config` (JSON 字符串)，存：

```json
{
  "enabled": true,
  "listen_port": 8388,
  "password": "xxx",
  "method": "2022-blake3-aes-128-gcm",
  "dns_primary": "https://1.1.1.1/dns-query",
  "dns_backup":  "https://8.8.8.8/dns-query"
}
```

不存到独立表，因为一台机器一份配置（SS 单一节点模型）。

## API

```
GET    /api/nodes/{id}/ss-config           读
PUT    /api/nodes/{id}/ss-config           写（不立即推送，只存 DB）
POST   /api/nodes/{id}/ss-config/apply     生成 JSON → scp 推送 → WS reload → 返回结果
GET    /api/nodes/{id}/ss-config/preview   返回将要推送的 sing-box JSON（用户看一眼放心）
```

分两步是因为：**"保存"和"应用"分离**，避免用户填错半截就把线上配置冲了。

## sing-box 配置生成器

文件：`backend/deploy/singbox_config.py`

按 `config_schema`（如 `singbox-1.10` / `singbox-1.13`）分支，**首版只实现一个分支**（当前最新 1.13），其他 schema 直接 `raise NotImplementedError("暂不支持 schema X")`，等出问题再加。

生成的最小可用 JSON：

```json
{
  "log": { "level": "info", "timestamp": true },
  "dns": {
    "servers": [
      { "tag": "doh-primary", "address": "https://1.1.1.1/dns-query" },
      { "tag": "doh-backup",  "address": "https://8.8.8.8/dns-query" }
    ],
    "strategy": "ipv4_only"
  },
  "inbounds": [{
    "type": "shadowsocks",
    "tag": "ss-in",
    "listen": "::",
    "listen_port": 8388,
    "method": "2022-blake3-aes-128-gcm",
    "password": "xxx"
  }],
  "outbounds": [
    { "type": "direct", "tag": "direct" },
    { "type": "block",  "tag": "block"  }
  ]
}
```

**不做分流/路由**，因为节点都是海外、用户已敲定"无分流"。`route` 字段省略，sing-box 默认走第一个 outbound = direct，符合"代理收到流量直接出本机"的要求。

## 推送流程

`apply()` 逻辑：

1. 从 DB 读 `ss_config` + `config_schema`
2. 调用生成器渲染 JSON
3. SSH 连节点，传四步：
   - `mkdir -p /etc/sing-box`
   - `cat > /etc/sing-box/config.json.new` (SFTP put 临时文件)
   - `/opt/mesh-panel/sing-box check -c config.json.new`（dry-run，失败立即 abort 不动旧配置）
   - `mv config.json.new config.json`
4. WS `send_cmd(node_id, "reload")` → agent 执行 `systemctl reload sing-box`
5. WS 收到 `ack` 后判断 ok，更新 DB 字段 `ss_applied_at` / `ss_apply_status`

**关键安全点**：先 dry-run 再 mv，**配置烂了不会把节点搞挂**。

## 前端

NodeList 操作列加一个按钮"**SS 配置**"，点开抽屉（不是 dialog，因为内容多）：

```
┌─ SS 配置 ────────────────────────────────────┐
│ ☑ 启用此节点                                  │
│                                              │
│ 监听端口   [ 8388         ]                  │
│ 密码      [ ********  ]  [生成]              │
│ 加密      [ 2022-blake3-aes-128-gcm  ▼]     │
│                                              │
│ 主 DNS    [ https://1.1.1.1/dns-query    ]  │
│ 备 DNS    [ https://8.8.8.8/dns-query    ]  │
│                                              │
│ [预览生成的 JSON]                            │
│                                              │
│ [仅保存]  [保存并应用到节点]                 │
└──────────────────────────────────────────────┘
```

`[生成]` 按钮：本地 `crypto.randomUUID()` 拼一个 base64 密码（2022-blake3 加密需要 16/32 字节）。

`[预览]` 弹小窗显示 sing-box JSON，只读，给用户检查。

## 不做的

- ❌ 一键导出 SS URI（用户已说不要订阅系统）
- ❌ 多端口/多用户（一节点一配置）
- ❌ 流量限制（第 5 块统计的事）
- ❌ TLS / WS 协议混淆（裸 SS 优先，后期想加再说）

## 验收

1. 给已部署节点填配置 → 应用 → 浏览器扫码或客户端测试能连上代理
2. 改密码 → 应用 → 节点上 sing-box 进程不重启（pid 不变）但密码生效
3. 故意填错加密方式 → 应用失败，节点旧配置不受影响（dry-run 拦下来）
4. agent 离线时点应用 → 提示"agent 不在线无法 reload，是否仅推送配置"
5. 多节点轮流应用，互不影响

## 实施顺序

1. 后端：加 ss_config 字段 + 配置生成器 + 4 个 API 端点
2. 后端测试：本机回环测一遍 generate / dry-run 拦截
3. 前端：抽屉 + 预览 + 保存/应用按钮
4. 真节点端到端测：本地客户端 → 节点 SS 端口 → 出网

## 待用户确认

1. **加密方式列表**给哪几个？我建议默认列表：
   - `2022-blake3-aes-128-gcm` ⭐（推荐，新协议、抗重放）
   - `2022-blake3-chacha20-poly1305`
   - `aes-256-gcm`（兼容老客户端）
   - `chacha20-ietf-poly1305`（兼容老客户端）
2. **DNS 默认值**：主 1.1.1.1 / 备 8.8.8.8 行不行？还是你想要 Quad9 / Cloudflare malware filter 这种？
3. **dns strategy**：`ipv4_only` 还是 `prefer_ipv4`？海外节点一般 ipv4_only 够用、避免 v6 问题。
